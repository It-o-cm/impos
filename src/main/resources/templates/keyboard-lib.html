{! ! THE shared input include: PosKeyboards renderers (price pad, search pad ! with digits, ALPHA keyboard — a FIXED 10-column grid needing ~554px ! minimum width) and the PosInput SINGLETON. CONTRACTS: PosInput.setup wires ! ONE input at a time (a second setup steals the buffer — one active binding ! per page); external pads can feed the same buffer through ! PosInput.handleKey(k); initialValue at setup and PosInput.prefill(v) later ! are the supported prefills (never poke .buffer directly). modes: ! 'integer'/'decimal'/'cents'/'text' govern what keys append. ! EVERY AMOUNT IS KEYED IN CENTS ('cents' mode), EVERYWHERE. The cashier keys ! 1 2 3 4 and the display reads 12,34: the comma is placed by the application, ! two digits from the right, and is never keyed. The buffer holds the digits of ! the cents, the display shows the euros and the hidden input posts the euros ! with a dot, so no server parses anything new. 'decimal' stays for the figures ! that are NOT amounts — a weight, a decimal quantity, a percentage — where the ! comma is part of what the cashier means. ! A PREFILLED VALUE IS A PROPOSAL, NOT A STARTED ENTRY. It is used only if ! the cashier validates it straight away: the first key of the pad takes the ! whole of it away. A till has no caret and no selection, so nobody can place ! themselves at the end of a default to extend it, and appending is what ! turned a 20 typed over a 45,30 due into 45,3020. ! THE DISPLAY IS NOT A FIELD. A till has no physical keyboard, so a visible ! there shows a caret waiting for keystrokes that never come — and ! invites someone to plug one in. Every display is a text element carrying the ! .pad-display class (the theme holds its height and its placeholder), and what ! is posted travels in a hidden input named by hiddenId. updateDisplay writes ! textContent on such an element and still writes .value on the few that are ! inputs, and padText(el) reads a display back whichever it is. !}
