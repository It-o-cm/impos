## 1. Méthode

Trois choses distinctes ont été vérifiées pour chaque ligne, dans cet ordre :

1. **Le site consommateur existe** — le `fichier:ligne` de la colonne *Preuve*
   a été ouvert, et la ligne de code relue. Quand l'audit du matin pointait un
   numéro devenu faux (les lots C1 et C4 ont décalé `PosSettingsService` de 92
   lignes), le site a été retrouvé par son contenu, pas par son rang.
2. **Un test l'exerce** — pas « mentionne la clé » : stube la valeur et assère
   un résultat observable.
3. **Le test est discriminant** — c'est le point qui a fait la différence.
   Un réglage stubé à une seule valeur ne prouve rien : si le consommateur
   remplaçait la lecture par un littéral égal à cette valeur, le test resterait
   vert. Sept lignes sur vingt-huit étaient exactement dans ce cas.

### La vérification par mutation

Chaque test écrit ici a été soumis à la mutation qu'il est censé attraper : la
lecture administrée a été remplacée par un littéral dans `src/main`, la suite
rejouée, puis le fichier restauré. **Les neuf mutations ont toutes été
attrapées, chacune par le test attendu et par lui seul** :

| Mutation appliquée à `src/main` | Test qui tombe |
|---|---|
| `showEan() &&` → `true &&` | `printTicketOmitsArticleEanWhenDisabled` |
| `Math.min(100, lineMaxDiscountPercent())` → `100` | `applyDiscountRefusesPercentAboveTheAdministeredLineCap` |
| `Math.min(100, globalMaxDiscountPercent())` → `100` | `applyGlobalDiscountRefusesPercentAboveTheAdministeredCap` |
| `MAX_DIMENSION = 128` → `4096` | `resizesToTheDefaultMaxDimension` + `defaultMaxDimensionBoundIsInclusive` |
| ajout de `store.code = trimmed(form, "code", …)` | `saveIgnoresAPostedStoreCode` |
| `data("groups", rows)` → liste vide | `listHandsTheTemplateTheWholeTree` |
| `family.buttonSize = size` → `"LARGE"` | `saveConfigStoresTheSmallSize` + `…TheNormalSize` |
| `compareTo(totalIncludingTax) > 0` → `>= 0` | `performRefundAcceptsFullTicketCoverage` |
| suppression de `product.internalCode = …` | `saveWritesEverything` |

C'est la seule preuve qui vaille pour un lot de vérification : un test qui ne
tombe sous aucune mutation ne démontre pas que le réglage est lu, il démontre
seulement que le code compile.

## 4. Résidus — ces deux lignes restent en `1a`

### `BO-03-10-19` — « tous les champs du magasin sont éditables »

**L'audit s'est trompé.** L'écran magasin écrit 10 champs sur 18. Sept champs
persistés de `Store` ne sont jamais alimentés par le formulaire :

| Champ | Déclaré | Conséquence |
|---|---|---|
| `legalName` | `Store.java:118` | **imprimé sur la facture** (`InvoiceDocument.java:296-303`) |
| `rcs` | `Store.java:125` | idem |
| `shareCapital` | `Store.java:132` | idem |
| `fax` | `Store.java:139` | idem |
| `theme` | `Store.java:79` | lu par `ThemeService.java:60` |
| `address.latitude` | `Address.java:51` | — |
| `address.longitude` | `Address.java:57` | — |

Les quatre premiers ne sont alimentés aujourd'hui que par l'import CSV
(`StoreCsvResource.java:222-228`) et le jeu de données initial. Le gabarit
`admin-store.html` ne porte que 10 `input name=`. Aucun test ne peut les
démontrer : le code ne les écrit pas.

**Câbler ces quatre champs légaux coûte quatre lignes dans `save` et quatre
champs dans le gabarit** — mais c'est une modification de `src/main`, que le lot
C0 s'interdit par définition. **À reprendre dans le lot C5.** Les trois autres
(`theme`, `latitude`, `longitude`) demandent un arbitrage : soit on les câble,
soit on les documente comme non éditables, comme c'est déjà fait pour `code`.

### `BO-03-01-17` — « bascule actif/inactif »

**L'exigence et le code ne parlent pas du même objet.** La bascule codée porte
sur un **article membre** (`AdminProductFamilyResource.java:313`,
`product.active = !product.active`), et elle est parfaitement démontrée dans les
deux sens (`AdminProductFamilyResourceTest:947` et `:965`). Mais `ProductFamily`
**n'a aucun champ `active`** : la bascule d'une **famille** n'existe pas.

→ **Arbitrage à rendre** (§5).

## 5. Arbitrages et hors périmètre

**Arbitrage — `BO-03-01-17`.** Deux issues, et une seule décision à prendre :
soit l'exigence vise l'article et elle est déjà satisfaite (il suffit de la
reformuler, zéro ligne de code), soit elle vise la famille et il faut construire
— champ `active` sur `ProductFamily`, action de bascule, et exclusion des
familles inactives des listings. Ce n'est pas du câblage : ça change le modèle.

**Hors périmètre, repéré et non appliqué :**

- `AdminTouchResourceTest` mocke `ImageResizeService` : aucun test ne relie
  l'écran des touches au redimensionnement réel. Un `verify` explicite sur le
  redimensionneur fermerait la jonction.
- `saveImages` apparie `imgCode[i]` et `imgData[i]` par index sans qu'aucun test
  ne pose deux paires valides simultanément : un glissement d'index passerait.
- Le format du code enseigne (deux lettres, `BO-10-03-01`) n'est validé nulle
  part, contrairement au n° de PDV qui a son `Pdv.isValidNumber`.
